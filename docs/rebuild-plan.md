# План переработки SIMAL

Дата аудита: 7 ноября 2026. Статус: новая версия реализуется; исходный план сохранён как карта работ.

Уточнение пользователя от 7 ноября: новые переводы проверять и исправлять, но не закрывать от индексации из-за языка или статуса проверки перевода. Sitemap и hreflang должны включать существующие индексируемые RU/EN/KA страницы.

## Цель и согласованные требования

Сделать поддерживаемый мебельный сайт вместо восстановленных страниц Bitrix: единый внешний вид, работающий каталог из Google Таблиц, корзина для заявки менеджеру и wishlist с сердечками.

- Google Таблицы — выбранный редактор ассортимента, цен и наличия.
- «Пометки» означают сердечки и избранное. Текстовые заметки, служебные метки и несколько личных списков не требуются.
- Повторяющиеся элементы используют общие компоненты, стили и состояния.
- Сценарий корзины и заявки берём из Sofiproftrade; внешний вид адаптируем к мебели и бренду SIMAL.
- GitHub остаётся хранилищем кода, Cloudflare — площадкой публикации.
- Дополнительные страницы и фотографии разрешено искать в поисковой выдаче Google/Яндекса и веб-архивах.

Исследованы текущая рабочая папка, каталог, импорт CSV, клиентские сценарии, API заявки, конфигурация публикации и соответствующие исходники Sofiproftrade. Два агента независимо проверили каталог/API и референс корзины. В браузере просмотрена уже открытая страница категории SIMAL. Полный мобильный и сквозной аудит отправки не выполнялся.

Пустое поле `image` не означает отсутствия всех фотографий в HTML или на диске. Нужно отдельно сопоставить существующие файлы, архивные ссылки и товары. В архивном `data/catalog.json` 292 записи, 277 уникальных ID и 1496 ссылок на изображения с `file:false`; этот флаг не заменяет проверку файлов.

В данных смешаны обозначения валют, включая `р.`. Пропущенную цену нельзя превращать в ноль, а архивные цены и наличие нельзя считать актуальными без проверки владельцем каталога.

Основные дефекты:

1. Импорт `tools/catalog_sheet.py` обновляет JSON, но не восстановленный HTML. Цена в карточке и цена в заявке могут разойтись.
2. `site/static/selection.js:70–73,224–225`: изменение списка пересоздаёт форму целиком, что может стереть имя и контакт.
3. `site/static/selection.js:279–281`: после успешной отправки сообщение записывается в старый DOM-узел после перерисовки.
4. `functions/api/quote.js:46–48`: неизвестный ID превращается в название позиции, вместо отклонения запроса. Изолированная проверка агента с mock fetch приняла неизвестный ID и телефон `x`; внешнее сообщение не отправлялось.
5. Нет постоянного серверного хранения заявок, дедупликации и надёжной повторной доставки уведомлений. Отправку в Telegram в текущей production-среде не проверяли.

## Рекомендуемая архитектура

Базовый выбор: Astro + TypeScript, статическая генерация страниц, общие компоненты и минимальный клиентский JavaScript. Для сложных интерактивных блоков корзины/избранного допустимы React-компоненты; весь сайт превращать в SPA не требуется. Astro позволяет отправлять готовый HTML и подключать интерактивность отдельными блоками: https://docs.astro.build/en/concepts/islands/.

```text
Google Таблицы: только публичные данные каталога
    ↓ импорт на сборке → проверка → версионный снимок
Astro: категории + карточки + поиск + JSON из одного снимка
    ↓
Cloudflare Pages: HTML, CSS, JS, изображения
    ↓ POST /api/quote
Pages Function / Worker → D1: заявка + позиции + очередь уведомлений
    ↓ повторяемая доставка
Telegram менеджера
```

Заявки, контакты посетителей, токены и служебные сведения не попадают в публичную таблицу или репозиторий. D1 подходит для хранения данных из Pages/Workers: https://developers.cloudflare.com/d1/.

Начальные фотографии можно хранить как проверенные оптимизированные файлы проекта. R2 добавить при необходимости отдельной медиатеки и частых загрузок: https://developers.cloudflare.com/r2/. Внутреннюю админку каталога в первую версию не включать; выбранный редактор — Google Таблицы.

Результат: воспроизводимая исходная точка, карта миграции, понятный способ отката.

## Этап 1. Данные и восстановление материалов

- Ввести неизменяемый ID товара; категории хранить отдельными связями. Повтор карточки в нескольких разделах не должен создавать новый товар.
- Различающиеся цвет, размер, комплектацию не склеивать только по названию или повторяющемуся старому ID: сначала установить, отдельный ли это вариант.
- Сохранить соответствие старых ID/URL новым; использовать его и для переноса существующего избранного/корзины, где соответствие однозначно.
- Отдельно хранить названия/описания RU, EN, KA, параметры, варианты, галерею, числовую цену, валюту `GEL`, наличие, порядок, SEO-поля и статус публикации.
- Разобрать все существующие локальные изображения, исходные URL в HTML, `data/catalog.json`, `tools/missing-images.txt` и архивные снимки.
- Для недостающего искать точный старый URL, артикул, модель, цвет и размер через Google/Яндекс, Wayback и источники поставщика. Для каждого восстановленного материала записывать URL источника, дату и соответствие товару.
- Не публиковать фотографию похожей модели как точную фотографию товара. У неподтверждённых записей сохранять статус проверки; архивные цены/акции/остатки не активировать автоматически.
- Отфильтровать посторонние архивные ссылки, например найденную ссылку на фитнес-абонемент.

Результат: чистый каталог, реестр восстановленных материалов и отдельный список того, что нужно получить у владельца.

Предварительный поиск уже обнаружил содержательные индексированные страницы: https://simal.ge/catalog/komody/komod-sirius-3-belyy77788804/, https://simal.ge/catalog/komody/komod-castor-3-dub-venge/, https://simal.ge/en/catalog/wardrobes/. В локальном дереве последняя категория отсутствует. Это кандидаты на восстановление; содержание ещё не импортировано. Прямой доступ к выдаче Google/Яндекса через использованный поисковый инструмент не удался, новые фотографии на этом этапе не подтверждены.

## Этап 2. Единые компоненты и внешний вид

- Оставить узнаваемый бренд SIMAL: логотип, красный акцент, спокойные нейтральные поверхности и крупные фото мебели. Подготовить читаемый вариант логотипа для выбранного фона.
- Задать общие токены: палитра, типографика, интервалы, ширина контейнера, сетка, рамки, радиусы и состояния фокуса.
- Собрать общие `Header`, `Footer`, `Navigation`, `Search`, `ProductCard`, `ProductPrice`, `Availability`, `QuantityControl`, `FavoriteButton`, `Button`, `FormField`, `Dialog`, `Notification`, `Breadcrumbs`.
- Главная, категория, подборка, избранное и корзина используют одни и те же товарные компоненты. Различия оформлять явными вариантами компонента, без отдельного набора похожих CSS для каждого раздела.
- Удалять старые стили Bitrix, inline-обработчики, заглушки BX и неиспользуемые зависимости по мере переноса. Не добавлять новые глобальные переопределения поверх старой системы.
- Шапку/подвал и контент собирать в HTML заранее, без клиентского XHR-включения.
- Нативные кнопки, подписи полей, клавиатурная навигация, видимый фокус, корректное закрытие диалогов, читаемые ошибки и достаточный размер интерактивных элементов.

Сначала сделать законченный вертикальный срез: одна категория → карточка товара → сердечко → корзина → форма. На нём согласовать визуальную систему, затем распространить общие компоненты на весь сайт.

Результат: один комплект компонентов и стилей, применённый ко всем повторяющимся элементам.

## Этап 3. Google Таблицы и публикация каталога

Предлагаемые листы:

| Лист | Назначение |
|---|---|
| Products | ID, категория/связи, SKU, цена, GEL, наличие, статус публикации, порядок |
| Translations | ID товара, язык, название, описание, SEO |
| Variants | ID варианта, ID модели, размер, цвет, комплектация, при необходимости своя цена/наличие |
| Images | ID товара/варианта, URL исходника, локальный файл, alt, порядок |
| Categories | Стабильный ID, родитель, названия/URL по языкам, порядок |

При небольшом ассортименте листы можно упростить, сохранив разделение ID, вариантов и переводов.

- Публичный CSV допустим только для данных, которые действительно разрешено публиковать. Иначе читать таблицу сервером/CI через API с минимальным read-only доступом.
- Первоначально запускать обновление каталога вручную из CI; затем добавить согласованный интервал обновления. Указать редактору, что изменение таблицы появляется на сайте после успешной сборки и публикации.
- Проверять уникальность ID, связи, числовые цены, валюту, обязательные поля, ссылки и изображения. Критическая ошибка останавливает новую публикацию и оставляет текущую рабочую версию.
- Генерировать из одного снимка HTML, карточки категорий, поисковый индекс и данные для заявки. Не поддерживать цены одновременно в HTML вручную и в отдельном JSON.
- Показывать время последнего успешного импорта в отчёте сборки; сохранять снимок данных для отката.

Результат: правка товара в таблице воспроизводимо обновляет все места его отображения.

## Этап 4. Каталог, поиск и страницы

- Главная: категории, понятное предложение магазина, выбранные товары, информация о шоурумах и доставке, прямой путь в каталог.
- Категории: работающие фильтры по фактическим характеристикам, сортировка, счётчик результатов, очистка фильтров, пустое состояние, пагинация при необходимости.
- Сохранять фильтры и сортировку в URL; на мобильном использовать выдвижную панель фильтров.
- Поиск по названию, артикулу, модели и ключевым параметрам, с понятным отсутствием результатов. Для текущего размера каталога достаточно локального индекса без внешнего платного сервиса.
- Карточка: галерея, цена/цена по запросу, наличие, варианты, характеристики, доставка, количество, «В корзину» и сердечко.
- Контакты, доставка/оплата, о компании и подтверждённые акции привести к тому же шаблону. Проверить реальные условия и адреса; не переносить правила оплаты Sofiproftrade автоматически.
- Предусмотреть RU/EN/KA в структуре с начала. Публиковать проверенные переводы; непереведённые товары не выдавать за полноценную локализацию и не генерировать фиктивные hreflang.

Результат: посетитель может найти подходящий товар и перейти к заявке с телефона или компьютера.

## Этап 5. Корзина, wishlist и заявка

Поведение по образцу Sofiproftrade:

- Сердечко на каждой карточке и странице товара; единый wishlist, активное состояние и счётчик в шапке.
- Из избранного можно добавить товар в корзину, не удаляя его из избранного.
- Корзина: количество, удаление, очистка с подтверждением, переход к товару, ориентировочная сумма известных цен. Неизвестную цену обозначать отдельно.
- Повторное добавление увеличивает количество. Корзина и избранное сохраняются после перезагрузки, согласуются между вкладками и языками по стабильному ID.
- При недоступном localStorage — понятное предупреждение и работа в памяти. Без регистрации сохранение между устройствами не обещать.
- Изменение количества, языка и состояния избранного не стирает форму заявки.
- Минимальная форма: имя, контакт (телефон либо email), необязательный город доставки и комментарий; точный набор определить по текущей работе менеджера. Согласие/уведомление об обработке данных оформить с реальными правилами магазина.
- Отдельные состояния загрузки, ошибок и успеха; блокировка повторного нажатия во время отправки; сохранение введённого при ошибке; видимый номер после приёма.
- Удалённые и недоступные позиции показывать явно; перед отправкой проверять их заново на сервере. Об изменении цены сообщать посетителю.

Сервер:

- Проверять формат контакта, длины строк, количество, допустимые ID/варианты и размер запроса. Цена и название берутся из опубликованного серверного снимка, а не из тела клиента.
- Сначала транзакционно сохранить заявку и позиции в D1 с уникальным `requestId`, затем записать событие уведомления. Повтор того же запроса возвращает тот же номер; иной payload с тем же ключом отклонять.
- Доставку Telegram выполнять повторяемо по сохранённой очереди, хранить статус и ошибки. Принятая заявка не исчезает из-за сбоя Telegram. Возможность дубликата уведомления при сетевой неопределённости учитывать, всегда включать номер заявки.
- Ограничение частоты, проверка Origin и защита от автоматического спама; Turnstile добавлять по выбранной схеме, не считать его заменой серверной валидации.
- WhatsApp — явная альтернативная кнопка с понятным статусом. Открытие WhatsApp не считать доказательством отправки или приёма заявки.
- При успехе вычитать только отправленный снимок корзины; добавленные во время запроса товары сохранять.
- Дать владельцу защищённый способ прочитать сохранённые заявки и статусы доставки; это небольшой операционный интерфейс/экспорт, а не отдельная админка каталога.

Результат: полноценный запрос менеджеру без онлайн-оплаты и без обязательного аккаунта покупателя.

## Этап 6. Оптимизация, SEO и выпуск

- TypeScript и явные схемы данных; отделить импорт, предметную модель, UI, состояние выбора и API. Одна команда сборки, lockfile и понятный README.
- Адаптивные изображения WebP/AVIF, размеры в HTML, lazy loading вне первого экрана; убрать лишние шрифты, библиотеки, архивные скрипты и дубли.
- Проверить старые URL: сохранить ценные адреса либо сделать точные 301. Без соответствия отдавать осмысленный 404/410; не перенаправлять весь удалённый каталог на главную.
- Canonical, sitemap, метаданные и корректные hreflang; BreadcrumbList/Product только по реальным данным. Корзину, wishlist, внутренний интерфейс и тестовую публикацию закрыть от индексации.
- Проверить мобильные размеры 360/390/768 px и desktop, отсутствие горизонтального скролла, ошибки консоли и битые ресурсы. Проверять фактическое поведение, а не только успешную сборку.
- Проверки данных и критических сценариев: добавление/удаление, wishlist, количества, ошибки хранилища, две вкладки, неизвестный товар, неверный контакт, повтор заявки, сбой Telegram после сохранения.
- Подключить GitHub CI: проверки → импорт → сборка → preview → production. Подтвердить текущий режим Pages: для Direct Upload возможен CI с Wrangler; не предполагать, что существующий проект можно переключить на Git integration без миграции. Документация: https://developers.cloudflare.com/pages/get-started/direct-upload/ и https://developers.cloudflare.com/pages/configuration/git-integration/.
- Перед выпуском проверить тестовый URL и контрольную заявку в согласованный канал, сверить запись в БД и получение уведомления. После публикации проверить production-URL, опубликованный commit и товары, затем зафиксировать способ отката коду и данным.
- Аналитику строить вокруг просмотра товара, добавления в корзину, начала оформления и принятой заявки; персональные контакты в события аналитики не передавать.

Результат: проверенная публикация, воспроизводимая сборка и инструкция редактирования каталога/обработки заявки.

## Порядок выполнения

1. Зафиксировать текущее состояние и способ публикации.
2. Очистить модель данных и собрать реестр материалов; поиск пропущенных фото можно вести параллельно.
3. Создать каркас приложения, общие стили и законченный образец категории/карточки/корзины.
4. Подключить Google Таблицы к единой генерации каталога.
5. Завершить поиск, фильтры, wishlist, корзину и серверную заявку.
6. Перенести остальные страницы и проверенные переводы, закрыть пропуски материалов и SEO.
7. Пройти сквозную проверку и выпустить через GitHub/Cloudflare.

Условия завершения: один товар имеет одинаковые данные и вид компонентов во всех разделах; правки таблицы обновляют все страницы; сердечки и корзина сохраняются; ошибка отправки не теряет данные; принятая заявка имеет номер и запись в БД; основные пути работают на мобильном; опубликованная версия и способ отката подтверждены.

Главная внешняя зависимость — актуальные цены/остатки, точные фотографии и проверенные переводы. Восстановление из индекса помогает заполнить пробелы, но не подтверждает актуальность коммерческих условий.
